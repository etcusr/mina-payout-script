# Isolated Mina batch payments implementation plan

**Goal:** Real signed zkApp multi-recipient transactions with configurable batch size, durable duplicate protection and devnet validation.

**Architecture:** Separate `batch-pay/` CLI and private SQLite journal. Native MINA signature-authorized account updates through pinned o1js; no deployment, no imports or writes to existing payout accounting. Mainnet submission remains disabled during testnet qualification.

**Tech stack:** Node >=22.19.5, o1js 3.1.0, node:sqlite, node:test.

**Spec:** User request: configurable true batches; testnet first, disconnections and duplicate protection; preserve all current payouts/accounting. Later prepare a 1 nanomina micro-test from the existing wallet.

## Constraints and review focus

- Amounts in exact integer nanomina, no floating-point calculations.
- Existing recipients by default; explicit `create:true` for controlled Devnet fixtures shows the 1 tMINA creation cost and protects account existence with on-chain preconditions.
- Network/chain identity, wallet, nonce, recipients and transaction hash bound to immutable intent.
- Persist uncertain state before submission; reconnect only reconciles, never automatically rebuilds or resends an uncertain transaction.
- Full recipient addresses; display fee, totals, nonce, hash and current/required confirmations.
- Duplicate plan creation, process races, restart after lost response, wrong network and invalid chain proof must fail safely.
- Production aliases/configuration/journal and wallet keys are not read or changed by this feature.

## Review ledger

- Independent review found hidden mutation retries in o1js transport. Replaced with a direct, single-attempt HTTP POST; transport-level regression failed at 3 calls, now passes at 1.
- Creation-fee account update exceeded the segment limit at 30 recipients. Combined the fee into the existing sender debit; real 30-new-account LocalBlockchain test now passes.
- Added competing-process claim, signed-only crash/stale nonce, historical operation reorg, and fresh chain identity immediately before submission tests.
- Known qualification scope: recent-chain proof only; old operations outside 290 blocks block future sends. No mainnet/production-accounting integration until an archive proof adapter and production signer are qualified.
