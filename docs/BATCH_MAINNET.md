# Mainnet batch pay

## Пакетные выплаты эпохи через обычные команды

`balance_mina` и `mina_pay` поддерживают пакетные выплаты для новых планов.
После локальных тестов включите их в своём приватном `config.yml`:

```yaml
PAYOUT_TRANSPORT: zkapp_batch
PAYOUT_BATCH_SIZE: 30
PAYOUT_BATCH_FEE_NANO: 6000001
```

В `config.example.yml` и библиотеке по умолчанию остаётся `payment`.
Существующие планы без поля transport остаются обычными платежами; настройки
не пересчитывают старые планы. Новый план фиксирует режим, размер и комиссию.
Получатели сортируются по адресу и делятся на последовательные пакеты.
Каждый пакет платит одну комиссию; при оплате делегаторами она делится поровну,
остаток в nanomina получают первые адреса в порядке сортировки. Адреса, которым
не хватает награды до положительной минимальной выплаты после своей доли
комиссии, исключаются с перерасчётом пакетов; их долг переносится.

Просмотр показывает полные кликабельные адреса, суммы, номера пакетов и комиссии.
Один ввод пароля обслуживает последовательную отправку пакетов с Applied + 3
между ними; выплаты прошлой эпохи заново проверяются на глубине 15. Прогресс
показывает nonce, полный хеш и глубину каждого пакета без повторения таблицы.
После перезапуска сначала сверяется уже отправленный пакет; для отправки
оставшихся неподписанных пакетов снова нужны подтверждение и пароль.
Неизвестный исход запрещает повторную отправку и сохраняет резерв.
Доказанный Failed списывает только комиссию и отменяет неподписанный остаток;
невыплаченная награда остаётся долгом. Автоматического перехода на обычные
платежи нет. Все получатели должны уже существовать в mainnet.

План эпохи связан с отдельным неизменяемым batch-планом. Подписанные намерения
и nonce хранятся в batch-журнале; подтверждённые результаты учитываются по
получателям для переноса долга и дохода владельца. Бюджет выплаты делегаторам
не списывается повторно как отдельный расход владельца. Оставшийся долг и
другие обязательства защищены. Временный заём из резерва для пакетов эпохи
запрещён; исключение для старого самостоятельного теста к ним не применяется.

## Самостоятельная batch-операция

Отдельная команда `batch_mainnet.py` отправляет настоящие zkApp-транзакции
нескольким получателям. Этот самостоятельный режим не изменяет сохранённые планы эпох, CSV, переносимые остатки
или строки обычного журнала. Его расходы оплачиваются из доступного дохода
владельца и отражаются в общей доступной сумме для вывода.

## Подготовка

Из корня проекта, с установленным Python-окружением и Node.js >=22.19.5:

```bash
npm ci --prefix batch-pay --ignore-scripts
```

Нужны рабочие `config.yml`, SSH-доступ к контейнеру Mina и зашифрованный ключ
кошелька выплат, зарегистрированный в ноде. Пароль вводится скрыто в терминале
только после показа и подтверждения плана. Ключ передаётся процессу подписи
через защищённое SSH-соединение и stdin; в файл, аргументы команды и журналы
ключ и пароль не записываются. Ключ в Devnet-каталог копировать не нужно.

## Просмотр и отправка

Команда ниже берёт **только адреса** из выбранного сохранённого обычного плана.
Суммы и состояние исходных выплат не изменяются. Замените `SOURCE_PLAN_ID`
на идентификатор нужного плана из своего журнала:

```bash
./venv/bin/python batch_mainnet.py preview \
  --source-plan SOURCE_PLAN_ID \
  --each-nano 1 --memo batch_test --operation batch_test \
  --batch-size 30 --fee-nano 6000001
```

`preview` проверяет сеть, архив, бюджет, наличие получателей и лимиты настоящих
транзакций. Сохраняет только отдельное предложение
`.payout-state/batch-proposals/batch_test.json`; ничего не подписывает и не отправляет.
Таблица показывает полные адреса, суммы, число пакетов, все комиссии и нехватку средств.
Если бюджет недостаточен или есть незавершённые обычные операции, отправка блокируется.

После просмотра:

```bash
./venv/bin/python batch_mainnet.py send \
  --proposal .payout-state/batch-proposals/batch_test.json
```

Программа повторяет проверки, запрашивает подтверждение, сохраняет неизменяемый
план и печатает его ID **до ввода пароля**. Затем подписывает и отправляет пакеты
по очереди, ожидая Applied + 3 блока для каждого. Для отдельной прошлой batch-операции
перед следующей отправкой требуется свежая архивная проверка с глубиной 15.

## Размер и комиссии

`--batch-size N` принимает 1–30 получателей на пакет. Например, 65 адресов при
размере 30 дают пакеты 30 + 30 + 5. У каждого отдельные nonce, хеш и комиссия.
Все пакеты проверяются на ограничения o1js до создания финансового резерва.
Автоматически увеличивать размер сверх заданного лимита программа не будет.

Для 24 адресов по 1 nanomina и размера 30:

| Статья | MINA |
|---|---:|
| Каждому | 0.000000001 |
| Всего получателям | 0.000000024 |
| Комиссия одного пакета | 0.006000001 |
| Всего с кошелька | 0.006000025 |

Это явно выбранная комиссия, а не обещание минимально возможной комиссии
или гарантированного времени включения. Все получатели должны уже существовать;
создание новых аккаунтов этим режимом не оплачивается.

## Обрыв связи и продолжение

Скопируйте точную команду `resume`, которую программа напечатала с ID плана:

```bash
./venv/bin/python batch_mainnet.py resume --plan BATCH_PLAN_ID
./venv/bin/python batch_mainnet.py status --plan BATCH_PLAN_ID
```

`resume` выполняет только сверку, без пароля и отправок. Если после сверки
остались ещё не отправленные пакеты, продолжение требует отдельного подтверждения:

```bash
./venv/bin/python batch_mainnet.py send --plan BATCH_PLAN_ID
```

Перед единственной попыткой отправки пакет получает постоянный статус неизвестного
исхода. Ошибка соединения, отсутствие в пуле или потеря ответа **не разрешают
повторную отправку**, смену nonce или создание заменяющего плана. Подпись, хеш,
nonce и резерв сохраняются. Если исход так и не найден в свежей цепочке, операция
остаётся заблокированной для расследования.

При доказанном Failed списывается только комиссия, последующие никогда не
подписанные пакеты отменяются, их резерв освобождается. Сам неудачный платёж
не повторяется автоматически. Подписанные и неизвестные пакеты не отменяются.

## Учёт и проверки

Новый журнал `.payout-state/batch-mainnet.sqlite3` отделён от обычного журнала.
Общий замок кошелька не даёт двум командам одновременно использовать nonce.
Обычные выплаты и вывод учитывают batch-расходы/резервы, а незавершённая
batch-операция блокирует конфликтующую отправку. Резерв делегаторов защищён.
Резервное копирование обычного состояния включает новый журнал.

Архивная сверка проверяет точный состав zkApp, порядок адресов, суммы, memo,
сетевую комиссию, nonce, native token, отсутствие дополнительных изменений
аккаунтов и включение в цепочку валидатора. Проверка исторических транзакций
расширяет поиск предков глубже последних 290 блоков.

```bash
./venv/bin/python -m unittest discover -s tests
npm test --prefix batch-pay
```

Сетевые тестовые отправки не входят в эти команды. Существующий публичный
[Devnet-тест](BATCH_DEVNET_VALIDATION.md) проверил потерю ответа без повторной
отправки.

17 ноября 2026 года завершён отдельный mainnet-тест: одна транзакция с memo
`batch_test`, 24 существующих получателя по 1 nanomina, комиссия 6000001 nanomina.
Проверены реальные подписи, Applied + 3 блока, все 25 AccountUpdate и отдельный
учёт 6000025 nanomina расходов без оставшегося batch-резерва. Обычный журнал,
переносимые обязательства и файлы текущих выплат не изменились. Хеш, полное
доказательство и резервная копия сохранены в приватном состоянии проекта.

Во время проверки обнаружено краткое отставание архива от нового блока. Batch-
сверка теперь повторяет только это чтение до трёх раз с интервалом 15 секунд;
несовпадение транзакции не повторяется и не считается подтверждением.

## Временное использование резерва по явному разрешению

По умолчанию резерв делегаторов недоступен для самостоятельной batch-операции. Для заранее согласованного
теста можно добавить к **preview из `--source-plan`** параметр
`--reserve-advance-nano 6000025` и выбрать отдельное имя `--operation`.
Это лимит временного дефицита покрытия в nanomina, включая комиссию, для одного
неизменяемого плана. Он сохраняется в предложении и журнале, показывается перед
отправкой и не может превышать полную стоимость операции. Изменить его через
`send --plan` или подменить готовое предложение параметром команды нельзя.

Разрешение не уменьшает обязательства делегаторам, не отменяет учёт расходов
владельца и не разрешает расходовать другие ожидающие переводы. После сверки
показываются текущий баланс, обязательства и сумма необходимого пополнения.
Остальные планы и обычные выплаты сохраняют стандартную защиту резерва.
