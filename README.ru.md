# mina-payout-script

[English](README.md) · **Русский**

Расчёт наград и выплаты для block producer'а [Mina Protocol](https://minaprotocol.com),
работающий с **собственной архивной нодой**, а не со сторонними API эксплореров.

Адаптирован под **хардфорк Mesa** (3 сентября 2026): 90-секундные слоты, coinbase
360 MINA, сброшенная нумерация эпох.

## Зачем свои данные

Публичные API экосистемы Mina состарились плохо. `graphql.minaexplorer.com`
перестал резолвиться, `api.minastakes.com` отдаёт 500-е, а бакет Foundation с
precomputed-блоками удалили без предупреждения. Всё, что было построено на них,
мертво.

Этот проект читает данные из **Postgres собственной архивной ноды** плюс GraphQL
демона для живого состояния. Единственная внешняя зависимость — публичный
GCS-бакет со стейкинг-леджерами, он пока поддерживается; а block guardian умеет
переключаться между несколькими зеркалами, когда одно из них исчезает.

## Что внутри

| Путь | Назначение |
| --- | --- |
| `calc_rewards.py` | Считает долю каждого делегатора, пишет `e<N>_payouts.csv` |
| `send_payout.py` | Рассылает выплаты по этому CSV |
| `withdraw.py` | Выводит комиссию валидатора на холодный кошелёк |
| `GraphQL.py` | Слой данных: SQL к архиву, GraphQL демона, кэш леджеров |
| `mina_client.py` | Небольшой GraphQL-клиент для кошелька и платежей |
| `redirects.py` | Логика перераспределения выплат |
| `vrf/probe.py` | Предсказывает выигранные слоты на эпоху вперёд |
| `archive/` | Docker Compose для архивной ноды с починенным guardian'ом |
| `scripts/` | Установщик, SSH-тоннель, алиасы |
| `calc.sh` | Обёртка над `calc_rewards.py` |

## Требования

- Python 3.9+
- **Архивная нода** Mina с доступным Postgres (см. [Архивная нода](#архивная-нода))
- **Демон** Mina с ключом кошелька выплат и доступным GraphQL
- `jq` (использует `calc.sh`)
- ~300 МБ диска на каждый закэшированный стейкинг-леджер

Демон и архив могут жить на удалённом сервере: всё общается с `127.0.0.1` через
SSH-тоннель.

## Установка

```bash
git clone https://github.com/etcusr/mina-payout-script.git
cd mina-payout-script
./scripts/install.sh
```

Установщик создаёт venv, ставит зависимости и копирует `config.example.yml` в
`config.yml`. Существующий конфиг он не перезаписывает.

## Настройка

Всё живёт в `config.yml`, который в gitignore. Начни с `config.example.yml` —
там расписан каждый ключ. Главное:

```yaml
VALIDATOR_ADDRESS: B62q...        # твой block producer
SEND_FROM_ADDRESS: B62q...        # кошелёк, куда идёт coinbase и с которого платим
WITHDRAW_TO_ADDRESS: B62q...      # холодный кошелёк для комиссии
VALIDATOR_FEE: 0.05               # 5%
GRAPHQL_HOST: 127.0.0.1
GRAPHQL_PORT: 3085
ARCHIVE_DB_URL: "postgresql://postgres:postgres@127.0.0.1:5432/archive"
```

**Пароль кошелька нигде не хранится.** `send_payout.py` и `withdraw.py`
спрашивают его при запуске скрытым вводом, так что он не попадает ни в историю
шелла, ни на диск.

## Подключение к ноде

Если нода удалённая, сначала подними тоннель — он пробрасывает и GraphQL демона,
и Postgres архива:

```bash
./scripts/tunnel.sh my-node --bg     # алиас из ~/.ssh/config, user@host, что угодно
./scripts/tunnel.sh --stop
```

GraphQL должен указывать на демона, у которого **есть ключ кошелька** — именно
там подписываются платежи. Если демон отдаёт GraphQL на другом порту (например,
из-за проброса в Docker):

```bash
REMOTE_GRAPHQL_PORT=6521 ./scripts/tunnel.sh my-node --bg
```

## Повседневная работа

### 1. Посчитать награды

```bash
./calc.sh                  # текущая эпоха, берётся у демона
./calc.sh 3                # эпоха 3
./calc.sh 3 --vrf          # плюс VRF-скан (см. ниже)
```

Пишет `e<N>_payouts.csv` — по строке на адрес получателя:

```
B62qDelegator...;3348000000000;3348.0;common;unlocked
адрес;наномины;мины;тип_делегации;статус_блокировки
```

### 2. Прочитать отчёт

```
==========================================================================
  EPOCH 0   chain tip 549218  |  canonical tip 548928  |  payout threshold 20 confs
==========================================================================

    height  time (UTC)          coinbase  archive    confs  note
--  ------  ----------------  ----------  --------  ------  ----------------
+   549174  2026-09-06 06:46         360  pending       44  ready to pay out
+   548900  2026-09-05 15:09         360  canonical    318  ready to pay out
~   549300  2026-09-06 09:12         360  pending        3  17 more blocks (~1h)
x   548501  2026-09-04 12:01         360  orphaned       -  orphaned, no reward
```

| Маркер | Значение |
| --- | --- |
| `+` зелёный | Подтверждений хватает, блок идёт в выплату |
| `~` жёлтый | Блок добыт, но ещё недостаточно глубоко |
| `x` красный | Ушёл в orphan, награды нет |

Колонка `archive` — это `chain_status` самого Postgres, он переключается на
`canonical` только на глубине K=290. Решение о выплате принимается по колонке
`confs` против `CONFIRMATIONS_NUM`.

Вердикт внизу говорит, что делать:

| Вердикт | Значение |
| --- | --- |
| `READY` | Эпоха закрыта, новых блоков не ожидается — можно платить |
| `PARTIAL` | Платить можно, но в эпохе ещё будет coinbase |
| `WAIT` | Блоки есть, но ни один не набрал нужной глубины |

`READY` может появиться **до конца эпохи** — если VRF-скан показывает, что
выигранных слотов впереди не осталось, ждать больше нечего.

### 3. Отправить выплаты

```bash
python3 send_payout.py --epoch 3
```

Читает `e3_payouts.csv`, разблокирует кошелёк, шлёт по транзакции на строку и
следит, пока каждая не попадёт в блок. Всё, что не подтвердилось за
`TX_CHECK_TIMER_SECONDS`, пишется в `failed_payouts_3.csv` для повтора.

### 4. Вывести комиссию

```bash
python3 withdraw.py --amount 252.5
python3 withdraw.py --amount 252.5 --to B62qOther...   # другой получатель
```

Сумма указывается вручную намеренно: баланс кошелька не учитывает выплаты,
которые ещё висят в мемпуле, и автоматическое «всё минус запас» легко отправит
деньги, уже обещанные делегаторам.

## Перераспределение выплат

Награда не обязана идти на адрес, который держит стейк. Два случая:

- ты стейкаешь с нескольких своих адресов и хочешь получать всё на один, вместо
  того чтобы потом собирать со всех
- аккаунт общий с кем-то, и награду надо делить

```yaml
PAYOUT_REDIRECTS:
  # всё на один адрес
  B62qMyStakingOne...: B62qMyMainWallet...
  B62qMyStakingTwo...: B62qMyMainWallet...

  # разделить между двумя людьми
  B62qSharedAccount...:
    B62qPartner...:      50
    B62qMyMainWallet...: 50
```

**Доля в пуле по-прежнему считается от стейкинг-адреса** — меняется только
получатель перевода. Несколько адресов могут вести на одного получателя, тогда
их выплаты сливаются в одну транзакцию.

Доли нормализуются, так что `50/50`, `0.5/0.5` и `1/1` означают одно и то же.
Последний получатель забирает остаток от округления, поэтому части всегда точно
складываются в исходную сумму.

`MINIMUM_PAYOUT` применяется к **итоговому переводу** после слияния — доля,
слишком маленькая сама по себе, всё равно учитывается вместе с остальными,
идущими на тот же адрес.

## Предсказание слотов через VRF

Mina вычисляет VRF для каждой пары (делегатор, слот) в начале эпохи, поэтому
выигранные слоты на **всю эпоху** уже определены. `vrf/probe.py` просит демона
повторить это вычисление:

```bash
python3 vrf/probe.py --epoch 0              # вся эпоха
python3 vrf/probe.py --epoch 0 --from-now   # только слоты впереди
python3 vrf/probe.py 619                    # конкретный слот
```

Результат кэшируется в `vrf/won_slots_epoch<N>.json` и переиспользуется в
`calc_rewards.py --vrf`, превращая расплывчатое «запланирован ещё один блок» в
точное «эпоха окончательно закроется 10 сентября в 03:05 UTC».

**Цена.** Каждая пара (слот, делегатор) — одна операция на эллиптической кривой
на ноде продюсера. Полная эпоха при 58 делегаторах это ~414 000 вычислений.
Демон Mina однопоточный (OCaml Async), поэтому потолок около 650 вычислений в
секунду — примерно 10 минут на эпоху, сколько бы ни было `--workers`. Лишние
воркеры лишь прячут сетевую задержку.

**Требования.** Ключ блок-продюсера должен разблокироваться в кошельке демона.
Скрипт разблокирует его, сканирует и блокирует обратно — при успехе, при ошибке,
по Ctrl+C и по SIGTERM. Follower-нода этого не умеет: у неё нет ключа продюсера.

## Архивная нода

В `archive/` лежит Docker Compose: Postgres, `mina-archive`, непроизводящий
демон, который его кормит, и **замена block guardian'у**.

```bash
cd archive
docker compose up -d
```

Подробности — в [archive/README.ru.md](archive/README.ru.md).

Коротко про guardian: штатный скрипт Foundation жёстко зашивает один S3-бакет.
Когда бакет удалили, скрипт начал бесконечно перезапрашивать один и тот же
недоступный блок, забивая логи сотнями строк в секунду.
`archive/scripts/blocks-guardian.sh` его заменяет: несколько зеркал с fallback,
валидация JSON, blacklist недоступных блоков и опрос демона о том, каких блоков
реально не хватает.

## Как устроен расчёт

1. **Стейкинг-леджер.** Скачивается по хэшу леджера эпохи из
   `gs://mina-staking-ledgers` и кэшируется в `archive/cache/ledgers/`
   (~280 МБ, качается один раз).
2. **Блоки.** Берутся из Postgres архива: блоки, созданные твоим валидатором в
   этой эпохе, без orphan'ов, с глубиной не меньше `CONFIRMATIONS_NUM`.
3. **Пул наград.** `coinbase + комиссии за транзакции - snark fees` по всем этим
   блокам. Coinbase читается из базы, а не хардкодится — Mesa урезала его с 720
   до 360.
4. **Разделение.** Каждому делегатору достаётся
   `пул * (его_стейк / общий_стейк) * (1 - комиссия)`. Для стейка Foundation и
   O(1) Labs можно задать отдельные комиссии (`VALIDATOR_FEE_FOUNDATION`,
   `VALIDATOR_FEE_O1LABS`); списки их адресов лежат в `foundation_addresses.txt`
   и `O(1)Labs.txt`.
5. **Фильтр.** Всё ниже `MINIMUM_PAYOUT` отбрасывается — не окупает комиссию.
6. **Редиректы.** Получатели переписываются по `PAYOUT_REDIRECTS` и сливаются.

Всё, что осталось на кошельке после выплат, — комиссия валидатора.

## Подтверждения и защита от реоргов

Блок становится безопасным для траты только когда он достаточно глубоко, чтобы
реорг не смог его убрать. Финальность протокола Mina — **K=290**, именно это
означает `chain_status='canonical'` в архиве, и это примерно 17 часов ожидания.

Измерено на полном архиве за всю эру Berkeley, 211 202 события реорга:

| Глубина реорга | Случаев |
| --- | --- |
| 1 | 210 827 (99,82%) |
| 2 | 339 |
| 3 | 26 |
| 4 | 7 |
| 5 | 1 |
| 6 | 1 |

Самый глубокий настоящий реорг за два года — **6 блоков**. (В данных есть ещё
выброс на 41 блок, но это хардфорк Mesa обрубил хвост Berkeley, а не реорг.)

`CONFIRMATIONS_NUM: 20` даёт больше чем трёхкратный запас над худшим
наблюдавшимся случаем и сокращает ожидание с ~17 часов до менее чем часа.
Поставь 290, если нужна строгая финальность протокола; рекомендация самой Mina
Foundation для бирж — 15.

## Что изменил хардфорк Mesa

Mesa активировалась 3 сентября 2026 в 18:00 UTC и поменяла несколько вещей, от
которых зависит этот скрипт:

| | Berkeley | Mesa |
| --- | --- | --- |
| Длительность слота | 180с | **90с** |
| Coinbase за блок | 720 MINA | **360 MINA** |
| Слотов в эпохе | 7140 | 7140 (без изменений) |
| Длина эпохи | ~14,9 дней | **~7,44 дня** |
| `global_slot_since_hard_fork` | непрерывный | **сброшен в 0** |
| Нумерация эпох | непрерывная | **сброшена в 0** |

Из-за сброса слотов выражение `slot_hf / 7140` стало неоднозначным: Berkeley
epoch 5 и Mesa epoch 5 дают одно значение. Эры различаются по
`protocol_version_id` в таблице `blocks` (1 = pre-Berkeley, 2 = Berkeley,
3 = Mesa) и определяются автоматически. Чтобы пересчитать историческую эпоху из
старой эры, задай `PROTOCOL_VERSION_ID` в `config.yml`.

`global_slot_since_genesis` **не** сбрасывался — поэтому проверки вестинга
делегаторов продолжают работать через форк.

Изменения схемы архива коснулись только zkApp-таблиц, так что здешние запросы
они не затронули.

## Диагностика

**`ModuleNotFoundError` сразу после переноса проекта**
В venv зашиты абсолютные пути, при переезде каталога он ломается.
Пересоздай: `rm -rf venv && ./scripts/install.sh`

**`No canonical blocks found for epoch N in the current protocol era`**
Либо в эпохе действительно нет блоков, либо ты запрашиваешь эпоху из старой эры
протокола. Задай `PROTOCOL_VERSION_ID` для нужной эры.

**`could not connect to server` на Postgres**
Тоннель не поднят. `./scripts/tunnel.sh <хост> --bg`

**`Couldn't find an unlocked key for specified sender` от `vrf/probe.py`**
`evaluateVrf` требует разблокированного ключа продюсера в кошельке демона.
Проверь, есть ли он вообще: `{ trackedAccounts { publicKey locked } }`. У
follower-ноды его нет никогда.

**VRF-скан отдаёт `nextBlockProduction: null`**
Ты обращаешься к фолловеру, а не к продюсеру. Направь `GRAPHQL_PORT` на ноду с
ключом блок-продюсера.

**Guardian бесконечно логирует один и тот же блок**
Это старый скрипт Foundation. Переключись на
`archive/scripts/blocks-guardian.sh`, как настроено в `archive/docker-compose.yml`.

## Безопасность

- `config.yml` содержит твои адреса и данные подключения к БД — он в gitignore,
  пусть там и остаётся.
- Пароли кошелька спрашиваются при запуске, нигде не хранятся и не логируются.
- `send_payout.py` и `withdraw.py` блокируют кошелёк обратно по завершении.
- `vrf/probe.py` разблокирует **ключ блок-продюсера**. Он блокирует его обратно
  через `finally`, `atexit` и обработчики сигналов, а если все попытки
  провалятся — печатает команду для ручной блокировки. Не выставляй GraphQL-порт
  демона наружу.
- CSV с выплатами содержат адреса делегаторов и суммы — они в gitignore как
  `*.csv`.
