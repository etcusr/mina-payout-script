# mina-payout-script

[English](README.md) · **Русский**

Точный расчёт наград и возобновляемые выплаты Mina через свою ноду и архив PostgreSQL. Основание для отправки — неизменяемый план и долговечный журнал SQLite. Старые CSV служат историческими доказательствами, а не очередью для повторной отправки.

## Установка и инициализация

Нужны Python 3.9+, зависимости из `requirements.txt`, полный архив, синхронизированный producer с ключом выплаты и SSH. `./scripts/install.sh` создаёт venv и копирует пример конфига, сохраняя существующий. Укажите адреса, денежную политику, `EXPECTED_CHAIN_ID`, реальный удалённый порт GraphQL, SSH alias и **SELECT-only** пользователя БД. Конфиг остаётся приватным.

```bash
./scripts/tunnel.sh --ensure
python3 payout_cli.py doctor --epoch 8 --wallet
python3 payout_cli.py init                   # только совершенно новая установка
# Для существующей истории сначала задайте LEGACY_PROTOCOL_VERSION_ID:
python3 payout_cli.py init --import-legacy
```

Импорт проверяет CSV/квитанции, фиксирует хеши и эру, не меняя исходные файлы или приватный ledger. Повторная инициализация существующего журнала запрещена. Отправленные/сверенные старые эпохи нельзя отправить заново. Утрата или повреждение состояния останавливает операции. Новый независимый каталог состояния не должен использоваться для обхода незавершённой выплаты.

## Обычная работа

Пошаговый пример: [выплаты за эпоху 7](docs/payout-epoch-7.ru.md).
Все относительные пути в командах отсчитываются от корня проекта.

```bash
mina_calc --epoch 7                 # либо личный balance_mina
mina_pay --epoch 7                  # подтвердить выплаты, затем дождаться сверки
mina_withdraw                       # вывести учтённый остаток дохода
```

Проверки и туннель уже встроены. `mina_pay` и `mina_withdraw` через обновлённые
скрипты автоматически делают копию до операции, ждут подтверждения, сверяют
учёт и делают итоговую копию. Отдельные doctor/dry-run/backup/reconcile и ручное
копирование UUID не нужны для обычного сценария. Алиасы не надо загружать заново,
если они уже работали: изменились вызываемые ими скрипты. Первый запуск функций
в новой оболочке без настройки: `source ./scripts/aliases.sh` из корня проекта.

Максимальное ожидание полного цикла — `AUTO_SETTLE_WAIT_SECONDS` (по умолчанию
3600). При таймауте код выхода 2 и явный pending; повторите ту же команду позже.
Ctrl+C возвращает 130 без сброса состояния и печатает команду продолжения. После явного --new-operation продолжайте по напечатанной команде без этого флага. Совпадающий завершённый вывод не
повторяется: для намеренно нового вывода той же суммы нужен `--new-operation`.
Низкоуровневые `payout_cli.py send/withdraw` сохраняют ручной режим, если не указан
`--complete`. Диагностические команды ниже остаются доступны по необходимости.

Подставьте закрытую эпоху. Для текущей эпохи доступен только **предварительный расчёт без отправки**. `--preview` позволяет отдельно пересчитать новую эпоху без плана и CSV. Старая оплаченная эпоха показывает исходный отчёт только для чтения: комиссия не угадывается по сегодняшнему конфигу. Готовый план возвращает сохранённый расчёт; изменение конфига его не меняет. `COMMISSION_SCHEDULE` задаёт комиссии по эре и начальной эпохе для будущих планов.

В плане зафиксированы staking inputs, хеш staking ledger из архива с учётом эры, хеши блоков, денежная политика, переносимые остатки и gross/net. План имеет SHA256 digest в `.payout-state/journal.sqlite3` и приватное представление `<digest>.plan.json`. CSV `era<ERA>_e<EPOCH>_owed.csv` и `..._payouts.csv` — совместимые выгрузки; `e<EPOCH>_*.csv` создаются только при отсутствии. Отправитель читает план из журнала, а не отредактированный CSV. По умолчанию пути привязаны к каталогу проекта независимо от cwd; `--project-root`, `--config`, `--state-dir` позволяют явно выбрать другую установку.

Перед подписью отправитель удерживает общую блокировку кошелька, проверяет ноду/архив, блоки плана, баланс, обязательства и mempool, спрашивает подтверждение и пароль, затем повторно получает свежие данные. **Intent и явный nonce сохраняются до sendPayment.** В `finally` выполняется попытка закрыть кошелёк, даже если ответ unlockWallet потерян. Пароль не сохраняется.

```bash
python3 send_payout.py --plan DIGEST --resume
python3 payout_cli.py reconcile --plan DIGEST          # проверка без записи
python3 payout_cli.py reconcile --plan DIGEST --commit
```

Таймаут, повреждённый ответ, потерянная квитанция или сбой локальной записи оставляют блокирующий uncertain intent. Возобновление ищет точное совпадение sender/nonce/recipient/amount/fee/декодированного memo в основной цепочке и mempool, но **не отправляет этот платёж повторно**. Отсутствие в mempool/архиве и истечение срока не доказывают неуспех. Неуспех может подтвердить только другая успешно применённая транзакция с тем же nonce и достаточной глубиной. Нельзя удалять/сбрасывать журнал для повторной выплаты.

Успешному платежу нужны `applied` в цепочке валидатора и **3 блока после блока платежа** (`TX_CONFIRMATIONS_NUM`). Перед расчётом и отправкой выплат следующей эпохи скрипт заново проверяет предыдущие выплаты и требует **15 блоков** (`PREVIOUS_PAYOUT_CONFIRMATIONS_NUM`); проверка повторяется после ввода пароля, до разблокировки кошелька. Вывод комиссии тоже проверяет предыдущие операции, но на обычном пороге 3. Сверяются отправитель, получатель, сумма, комиссия, memo, nonce, хеш, сеть и принадлежность цепочке. Историческая выплата без проверяемых квитанций блокирует новую отправку. Созревание наградных блоков (`CONFIRMATIONS_NUM`) остаётся отдельной проверкой.

Явный `TX_CONFIRMATIONS_NUM` применяется и к существующим планам: суммы, memo и хеш плана не переписываются, фактический порог сохраняется в доказательстве подтверждения. Новый план без настройки получает порог 3; старый без явного переопределения сохраняет свой порог. Уже работающий процесс использует загруженные при запуске настройки.

На экране каждого платежа отображается `Applied · подтверждения 1/3`, затем `2/3` и зелёное `3/3 · готово`; фактическая глубина может быть больше порога. Перед следующей эпохой отдельно виден результат проверки предыдущих выплат, например `18/15`. Полные адреса — ссылки MinaScan, цвета обозначают успех, ожидание и проблему. При выводе в файл цвет и ссылки терминала отключаются; `NO_COLOR=1` отключает цвета, `NO_HYPERLINK=1` — ссылки, `MINA_DEBUG=1` включает технический schema probe.

Таймаут ожидания оставляет возобновляемый pending, `--wait-seconds 0` отключает ожидание. Пользовательские скрипты завершают сверку автоматически; в ручном режиме это делает `reconcile --commit`. Сверка повторно проверяет доказательства, идемпотентна и переносит недоплаты. Даже пустой/dust-only план нужно сверить, чтобы сохранить кредит. Реорг блокирует дальнейшие действия; автоматического отката старой истории нет. `--force`, `--accept-pending` и финансовый commit по CSV запрещены.

Если после отправки пропадает связь с нодой, ожидание проверяет туннель и повторяет только сверку в пределах `--wait-seconds` / `AUTO_SETTLE_WAIT_SECONDS`. Новых отправок в этом цикле нет. При истечении времени выводится, что связь недоступна и подтверждения неизвестны; журнал и резерв сохраняются. Ошибки сети блокчейна, целостности архива и доказательств этим повтором не скрываются. Если SSH недоступен ещё при запуске, сначала нужно восстановить доступ к серверу, затем повторить исходную команду.

## Точная арифметика и вывод комиссии

`mina_withdraw` без `--amount` подставляет остаток дохода из БД: комиссию валидатора и оставшиеся на кошельке награды своих адресов, минус расходы на выплаты, предыдущие выводы и комиссию нового вывода. Уже отправленные своим адресам выплаты делегаторам показываются отдельно и повторно не включаются. Адреса берутся из `config.yml`; адрес назначения — `WITHDRAW_TO_ADDRESS`.

Начальный учёт этого кошелька начинается с эпох 6 и 7. Старые переводы до установленной границы учёта не распределяются задним числом между этими эпохами. Последующие начисления записываются при завершении сверки выплат, один раз на эпоху. До отправки вывод резервируется в журнале: потеря ответа или перезапуск продолжают ту же операцию; успешный вывод уменьшает остаток. При нулевом остатке повторный вызов ничего не отправляет. Неучтённая исходящая операция после начала учёта блокирует автоматический вывод до выяснения. Резервные копии включают таблицы дохода и выводов; существующий журнал обновляется до схемы 3.

Ручной `--amount` сохранён и тоже учитывается как расход. Автоматический режим не продолжает незавершённый ручной вывод с произвольной суммой: для него нужна напечатанная команда продолжения. Для проверки без отправки: `mina_withdraw --dry-run`.

После успешной сверки выводится итоговая таблица по обновлённой БД: выведено с комиссиями, осталось до комиссии следующего вывода и зарезервировано с комиссиями. Она также показывается при повторном вызове, когда нового дохода для вывода нет.

Комиссии и staking balance читаются сразу как Decimal, доли считаются рационально без float. Параметры vesting обязательны, конечны и неотрицательны; финальный unlock использует округление числа периодов вверх. Нулевой период открывает баланс на cliff, нулевой increment с положительным остатком не открывает его в диапазоне слотов протокола. Вознаграждение каждого staking address округляется вниз до nanomina; остаток остаётся валидатору. Получатели redirect сортируются, последний получает целый остаток. После объединения адресов применяются исключения собственных адресов, signed carry и минимальная выплата. Положительный carry означает долг пула, отрицательный — переплату. Gross, собственная исключённая доля, доля валидатора и paid/carry сохраняются точно; правила supercharged сохранены.

`PAYOUT_REDIRECTS` принимает адрес или словарь адресов с положительными весами. Неверные адреса, NaN/отрицательные значения, повреждённые квитанции, дубликаты и неверные redirects останавливают расчёт. В старом CSV истина — nanomina-колонка; отображение MINA может отличаться на 1 nanomina. Новые выгрузки согласованы точно.

```bash
python3 withdraw.py --amount 12.345678901 --to B62... --dry-run
python3 withdraw.py --amount 12.345678901 --to B62...
# Возобновлять ТУ ЖЕ операцию с UUID, показанным перед вводом пароля:
python3 withdraw.py --amount 12.345678901 --to B62... --operation-id UUID
python3 payout_cli.py reconcile --plan WITHDRAWAL_DIGEST --commit
```

Вывод использует общий журнал/lock, свежие проверки, nonce и lock-finally. Незавершённый/несверенный план выплат или старая несверенная выплата блокирует вывод. Резервируются положительные carry и объединение локальных/mempool обязательств без двойного учёта одного платежа. Неснятая комиссия прошлых эпох не добавляется к начислениям следующей. Доход учитывается отдельно в БД, при этом баланс кошелька общий. Автоматический вывод ограничен учтённым доходом и свободным балансом после резервов. Перед ручным выводом рассчитайте и сверяйте закрытые эпохи: один баланс не определяет доход владельца. Dry-run не открывает кошелёк и не создаёт withdrawal plan.

Опциональные приватные `ledger.py`/`payout_ledger.json` сохраняют прежнюю историю. В публичной установке carry хранится в журнале и используется `payout_cli.py reconcile`; приватный `reconcile.py` — совместимая обёртка. Утрата импортированного ledger останавливает учёт. Балансы и полная история приватного ledger сверяются с неизменяемым снимком инициализации и последовательностью settlements журнала. Восстановление только старого ledger, удаление digest-записи или незаписанная правка carry останавливают операции. Сбой после записи ledger, но до journal восстанавливается только сверкой точного pending digest после свежих доказательств; остальные операции в этом промежутке заблокированы, повторной дельты нет.

## Статус и восстановление

```bash
python3 payout_cli.py status                         # офлайн, без инициализации
python3 payout_cli.py status --epoch 6               # исходная старая история
python3 payout_cli.py status --epoch 6 --online      # свежие точные доказательства
mkdir -p ./.payout-state/backups ./.payout-state/restore-checks
python3 payout_cli.py backup --destination ./.payout-state/backups/new-name
python3 payout_cli.py restore --backup ./.payout-state/backups/new-name --destination ./.payout-state/restore-checks/new-name
```

Backup под wallet lock сохраняет SQLite, CSV, конфиг и опциональный ledger с контрольными суммами и приватными правами. Restore сначала проверяет хеши/схему и создаёт **новый отсутствующий каталог**, никогда не заменяя рабочий. Резервная копия содержит учётные данные и финансовую историю. Для проверки восстановленного каталога используйте `--project-root DEST --state-dir DEST --config DEST/config.yml`. Переключение рабочего состояния выполняется отдельно оператором; нельзя одновременно запускать исходную и восстановленную установки.

Интегрированный журнал имеет схему **3**. Журнал схемы 2 автоматически обновляется при открытии; перед обновлением сохраните проверенную резервную копию. Автоматического изменения экспериментальной схемы 1 нет: сначала сохраните backup и разрешите имеющиеся intents, затем нужна проверенная миграция. Переход со старого скрипта выполняется через `init --import-legacy` без изменений старых файлов. Откат кода не разрешает запускать старый небезопасный sender для уже отправленных новых планов. Сохраните все состояния и восстанавливайте только в новый каталог. Несверенные старые выплаты без установленного учёта требуют отдельной проверенной миграции; импорт не угадывает paid/unpaid.

## Проверки и ограничения

`status` и `plan --json` выводят один JSON-документ в stdout; диагностика и прогресс загрузки/VRF идут в stderr.

`doctor` проверяет producer/chain identity, SYNCED, непрерывность canonical и parent links, дубликаты/устаревшие статусы, родословную от текущего producer tip, эру, допустимое отставание canonical; по запросу — баланс/nonce/mempool. Финансовые операции обновляют проверки. Идентификатор staking ledger берётся из архивного `epoch_data`, а не по дате объекта в bucket.

Это не replay консенсуса/ledger, не доказательство полноты каждого internal/user command, не криптографическая проверка Merkle root загруженного staking ledger и не замена контролю диска/PostgreSQL. Корректные блоки с нулевым coinbase поддерживаются. Повреждённые обязательные поля и расхождение выборок наград/блоков останавливают расчёт; фактические входы включены в fingerprint.

`calc.sh`, `mina_calc` и `balance_mina` автоматически проверяют оба SSH-forward endpoint, в том числе при явной эпохе. Исправный ручной туннель переиспользуется. Создаются только отсутствующие forwards; чужой занятый порт вызывает ошибку. `--stop` закрывает только собственное SSH control connection. Порты окружения и `MINA_SSH_HOST` согласованы общим config loader. Достаточно существующего подключения `scripts/aliases.sh`.

`--vrf` и `--vrf-refresh` сохраняют явный запуск VRF cache/scan: он может запросить пароль BP и идти несколько минут, но не разрешает выплаты. Настройка архива: [archive/README.ru.md](archive/README.ru.md). Ключи, конфиг, runtime state, CSV, приватный ledger/reconcile и `CLAUDE.md` остаются gitignored.

```bash
venv/bin/python3 -m unittest discover -v
```

Финансовые тесты используют только fake adapters и временные каталоги. Публичная копия пропускает тесты опционального приватного ledger. Live-проверка развёртывания — `doctor` и read-only `status`, без настоящего платежа.
